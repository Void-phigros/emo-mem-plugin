# 压缩 Prompt 参考与最佳实践

本文档说明 `compressor.py` 中压缩 Prompt 的设计要点和调优建议。

## 系统 Prompt 要点

压缩时要求 LLM 遵守以下规则：

1. **只输出 JSON**：不输出任何解释、注释或 markdown 代码块标记
2. **区分事实与情感**：事实骨架记录"发生了什么"，情感层只记录"怎么说"
3. **不编造事实**：无法确定的字段写 `null` 或空数组 `[]`
4. **保留关键信息**：承诺、约定、未解决项、关键人物关系与因果
5. **情感必须绑定对象和强度**：同一"焦虑"可能原因不同，必须区分
6. **原文锚点最多 3 条**：只保留关键承诺、高情绪强度、容易歧义的原句
7. **importance 取 0~1**：高情感强度 / 高重要性 / 未解决项应取较高值
8. **decay_policy 合理选择**：高重要性或未解决项用 `slow` 或 `never`
9. **source_turns 填轮次编号**：便于追溯来源
10. **relationship_state delta 取 -1~1**：表示相对变化

## 生成控制原则

> **先事实骨架，后情感修饰。**

生成流程：

1. 先输出事件框架/开头句，锁定事实、意图和边界
2. 再根据后台情感状态变量调节语气、共情方式、措辞和防御程度
3. 情感层只影响"怎么说"，不直接编造"发生了什么"
4. 对关键事实使用原文锚点或事实骨架校验

## 压缩倍数估算

基线：100万上下文窗口，每天约200句，约150天（~33 token/句）。

| 压缩倍数 k | 预计天数 | 约合 |
|---|---|---|
| 2 | 300 | 10个月 |
| 3 | 450 | 15个月 |
| 5 | 750 | 约2年 |
| 10 | 1500 | 约4年 |
| 20 | 3000 | 约8年 |

> 注意：这是"仍把记忆塞进窗口"的估算。若改为"固定窗口 + 外部记忆库"，
> 天数上限由检索与聚合能力决定，现实工程预期约 1~3 年后再做分层重建。

## 推荐压缩参数

| 参数 | 推荐值 | 说明 |
|---|---|---|
| `n_turns` | 20 | 每 20 轮压缩一次 |
| `max_inject_memories` | 3 | 最多注入 3 条相关记忆 |
| `max_anchors` | 3 | 每条记忆最多 3 个原文锚点 |
| `time_decay_half_life` | 30 天 | 30 天半衰期 |

## 风险与边界

1. **情感标签有歧义**：同样"焦虑"可能原因不同，必须绑定对象和事实骨架
2. **有损压缩**：情感概括适合人格/语气一致性，不适合精确事实召回
3. **错误归因**：只靠情感检索会错误归因，必须用混合检索
4. **检索错误累积**：多轮对话中检索错误会累积，必须保留原文锚点和校验
5. **模拟情感需要状态变量**：不能只靠文本写"我很共情"，需要内部状态变量
6. **操纵与隐私风险**：插件应声明风险等级和权限
7. **长期记忆需要遗忘机制**：低强度日常记忆应衰减或合并

## LLM 接入

`compressor.py` 的 `call_llm()` 默认尝试使用 `openai` SDK。

接入真实 LLM 时：
- 设置 `OPENAI_API_KEY` 环境变量
- 或修改 `call_llm()` 使用其他 SDK（Anthropic、Azure 等）
- 建议使用 `response_format={"type": "json_object"}` 强制 JSON 输出

LLM 不可用时自动回退到规则式压缩（`fallback_compress`），保证可测试性。
